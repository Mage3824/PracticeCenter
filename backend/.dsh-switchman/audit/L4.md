## 4.3 Граничные случаи (что реально произойдёт)

- finish без start → 409 BR2 (`WorkTimeService.cs:104-109`). Двойной finish → 409 BR2. Двойной start → 409 BR1 (только пока смена Active).
- start после finish в тот же день → **новый WorkDay** (`DevRepositories.WorkTime.cs:151`) и часы складываются в `HoursByDay` (`ReportService.cs:276-283`).
- перерыв без рабочего дня → 404 `WorkDay`; finish перерыва без start → 404 `Break`/`WorkDay`; finish закрытого перерыва → 409 BR10.
- `endTime` < `startTime` дня → 200, `CountedInReports = false`, отрицательные минуты в daily report (`ReportService.cs:166`, `DailyReportWire.totalMinutes`).
- пересечение полуночи: `StartTime/EndTime` — TimeSpan, дата отдельная (`Entities.cs:28-42`); finishpayload не содержит дату (`Requests.cs:47-51`) → закрытие «вчерашней» смены сегодня даёт отрицательную длительность; авто-закрытия, которая должна это разрешать, нет (БП3).
- авто-закрытие открытого перерыва моментом `endTime` раньше его старта → `Duration < 0`, `EndTime < StartTime` (`WorkTimeService.cs:194-211`).
- границы отчёта: inclusive `>=`/`<=` по датам (`DevRepositories.WorkTime.cs:181`, `DevRepositories.Support.cs:126`); конец месяца через `firstOfNextMonth.AddDays(-1)` (`ReportService.cs:343-347`) → декабрь/високосный февраль корректны.
- деактивация пользователя: вход блокируется, но в месячном отчёте сотрудник исчезает (`GetActiveEmployeesInDepartmentAsync`) — против БП24.
- удаление отдела: 409 при детях/сотрудниках (`DepartmentsController.cs:139-175`); PUT допускает двухшаговую петлю родителей (guard только `SELF_PARENT`).
- отсутствие отчёта → `null` 200 (BR15), дублирование отчёта отсутствует на уровне сервиса (переиспользуется существующий, `ReportService.cs:81-116`) но возможно в гонке (см. 4.4).
- закрытый период не блокирует правку отчёта; повторное close → 409 BR23.1, reopen незакрытого → 409 BR23.2 (`AdminController.cs:78-83, 117-122`).
- отсутствующий/некорректный `Id` → 404 `ENTITY_NOT_FOUND`; GUID в маршруте парсится MVC, пустой Guid → 404.

## 4.4 Concurrency (in-memory)

- Два `POST /start` одного пользователя: оба проходят проверку BR1 (`WorkTimeService.cs:58-68`), оба пишут без lock (`:82`) → два активных дня; следующий finish закрывает один, второй висает.
- Одновременный finish и start/finish перерыва: мутация сущностей под `EntityMutationGates.WorkTime` (`WorkTimeService.cs:115,154,194`; `BreakService.cs:128`), но сами репозитории (`Dictionary`) синхронизации не имеют → `foreach` по `_workDays` (`DevRepositories.WorkTime.cs:148-160`) одновременно с `SaveAsync` (`:167`) может дать `InvalidOperationException` → 500.
- Два `POST /api/reports/{workDayId}` на один день: read-modify-write без lock (`ReportService.cs:81-120`) → два `Report` на один `WorkDayId`, последний текст побеждает.
- `SetAbsence` под `EntityMutationGates.Absences` (`AbsenceService.cs:56`) — ok; BR20 под `UserMutationLock` — ok.
- На EF Core без транзакций те же гонки становятся «lost update»; нужны: уникальный индекс `(UserId, Date)` для активных смен, уникальный индекс `Report.WorkDayId`, оптимистичная конкурентность или транзакция на read-modify-write, и `SaveChangesAsync` вместо синхронного `GetAwaiter().GetResult()` внутри lock (`WorkTimeService.cs:120,125,163,210` — deadlock-риск с реальным DbContext).
