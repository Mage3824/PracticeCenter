интеграционный слой равен по количеству unit-слою, хотя интеграционных тестов должно быть
меньше (ориентир 2–3 unit на 1 integration). Дефицит именно в integration-слое: непокрытые
эндпоинты департаментов, экспорт (CSV/501), аудит-логи, EmployeeOnly-эндпоинты для чужой роли.

## 2. WebApplicationFactory: изоляция, скорость, авторизация

Что есть:
- `ApiHarness.CreateAsync()` создаёт **новый** `new WebApplicationFactory<Program>()` на каждый
  тест (`IntegrationApiEndpointsTests.cs:174-183`), сидирует 4 пользователей (`:194-214`) и
  получает 4 JWT реального логина (`:178-181`). `Dispose()` закрывает client и factory (`:188-192`).
- Реальные токены: тесты ходят в API с настоящим Bearer (не фейковые claims) — хорошо.
- DI-репозитории синглтонные (`Program.cs:53-61`), но хост новый на каждый тест → состояние
  не перетекает между тестами; в `DevRepositories.*` нет статической изменяемой состояния
  (`DevRepositories.Users.cs:17`, `DevRepositories.Support.cs:11,134,194` — instance-словари;
  статические только чистые хелперы `TryWithinPeriod`). То есть **загрязнение state не обнаружено**;
  взаимозависимость тестов отсутствует, `IClassFixture` не используется.
- `ConfigureTestServices` меняет только `ILoggerFactory` на `NullLoggerFactory` (`:176`).
- `Program.cs:28,242` — `public partial class Program`, поэтому фабрика работает без InternalsVisibleTo.
- Сид dev-данных гейтед `IsDevelopment() && IsManualRun()` (`Program.cs:171`) → в тестовых
  хостах не протекает (и, наоборот, сам сидер не тестируется).

Проблемы:
1. **Нет `UseEnvironment("Testing")` и нет переопределения `JwtSettings`** (`:176`). Токены
   подписываются dev-секретом из `src/WorkTime.Api/appsettings.json:3`
   («work-time-development-signing-key-change-me-please-32+-bytes»), issuer/audience/expiry тоже
   из файла. Тесты молча зависят от боевого конфига: его правка ломает сьют, а окружение
   «Development» в фабрике может включить env-гейты.
2. **Белая.Box-манипуляция временем**: `SessionExpired_After8HoursOfInactivity_Returns401_BR32`
   откатывает активность синглтонного `UserActivityTracker` через `api.FactoryServices`
   (`:186`, `:1195-1197`) — ассерт на внутренности реализации, а не на поведение; `IClock` нет.
3. **Флаккость по часам**: даты в integration-тестах из `DateTime.UtcNow` (`Today`, `:166`);
   при переходе UTC-суток тесты BR1/BR27/BR28/BR14/BR15/BR16 и BR35 «до конца дня»
   расходятся; BR3 (23:59:59) вообще нельзя воспроизвести детерминированно.
4. **Скорость**: 26 хостов × 4 `PasswordHasher.TryHash` + до нескольких `TryVerify` за тест;
   Argon2id `m=19456 KiB, t=2` (`src/WorkTime.Application/PasswordHasher.cs:12-13`) → десятки
   секунд суммарно, последовательно (все integration в одном классе = одна xUnit-коллекция).
   `xunit.runner.json` отсутствует → нет настройки параллелизма/long-running.
   Меры ускорения и изоляции: `IClassFixture<WebApplicationFactory<Program>>` + `ResetAsync()`
   (очистка синглтонных репозиториев через `FactoryServices`), отдельный дешёвый тестовый
   PasswordHasher/параметры (`MaxIterations`, меньший `MemorySize`), `UseEnvironment("Testing")`,
   `xunit.runner.json` с `parallelizeTestCollections`.
5. `[Collection]`/`DisableParallelization` нигде не объявлены; unit-классы параллельны между
   собой — это нормально для фейков, но при переходе на EF нужно явное разделение коллекций.

## 3. Негативные и security-тесты: покрыто / нет

Покрыто: 401 анонимный запрос (`:435`), 403 employee на admin/manager-эндпоинтах (`:464`,
`:473-506`), 409 BR1/BR6/BR10/BR14/BR12/BR21/BR20/BR27/BR23 с `code`+`status` в ProblemDetails
(`:615-619`, `:639-640`, `:660-661`, `:728-729`, `:754-755`, `:785-786`, `:917-918`, `:988-989`,
`:1022-1023`), 400 + ProblemDetails (type/title/status) (`:1034-1057`), 404 ProblemDetails
(`:1161`), BR32 в обе стороны (`:1183`, `:1228`), BR24 деактивация (`:408`, `:878`), BR35
unlock администратором (`:940`), BR36 капча на 2-й неудаче (`:362`).

Нет (конкретные дыры):
- `/api/departments/*` — 6 эндпоинтов, все с политиками (`DepartmentsController.cs:33-140`) — **ноль тестов**.
- `/api/reports/monthly/export.xlsx` → 501 (`ReportsController.cs:183-200`) — не тестируется;
  CSV-экспорт BR17 (`ManagementWires.cs:146-147`) — не тестируется (content-type, BOM, `;`).
- 501 как класс ответов вообще нигде не ассертируется.
- 401/403 ассертируются только по статусу, без тела/`code` (контракт ProblemDetails для
  authentication/authorization не проверяется).
- EmployeeOnly-эндпоинты для manager/admin (например `POST /api/work-days/start` руководителем) — не тестируется.
- Токен: не проверяются tampered signature, expired token, wrong audience/issuer.
- Concurrency/race: ни одного `Task.WhenAll`/параллельного запроса в тестах (grep не нашёл);
  гонки BR1 (двойной старт), BR10 (двойной перерыв), BR20 (последний админ) не проверены,
  хотя в src есть `lock (EntityMutationGates.Users)` (`AuthService.cs:103`).
- Деактивированный/заблокированный пользователь: деактивация покрыта, «заблокирован до конца
  дня» (10 неудач) — нет.

## 5. Качество тестов

- **Unit-тесты ассертируют поведение**: код бизнес-исключения (`Assert.Equal("BR1", ex.Code)`,
  `:66`, `:120`, `:161`, `:367`; ReportService `:57`, `:175`, `:359`; BreakService `:192`),
  вычисленные величины (часы/минуты, `CountedInReports`, флаг лимита перерывов), тип исключения
  для отсутствующей сущности (`EntityNotFoundException` с `EntityId`/`EntityType`, `:200-204`).
  Это хорошая практика.
- **Integration-тесты частично ассертируют реализацию**: `BackdateActivity` через root
  `IServiceProvider` (`:186`, `:1195-1197`), сравнение буквально `"null"` как тела (`:353`, `:588`)
  — хрупкие, но соответствуют контракту §2.
- **Дублирование Arrange**: каждый unit-тест заново собирает 5–6 репозиториев
  (`WorkTimeServiceTests.cs:28-33` во всех 9 фактах, аналогично Report/Absence/Break/Auth) —
  boilerplate без shared-helper; хелперы есть только в integration-файле (`:516-532`, `:704`).
- **Ключевой структурный дефект**: unit-тесты работают на фейках `InMemory*Repository` из
  `tests/WorkTime.Tests` (global namespace), а рантайм Api привязывает одноимённые классы
  `WorkTime.Infrastructure.InMemory*Repository` (`Program.cs:53-61`, `DevRepositories.Users.cs:7-8`
  с прямым комментарием о намеренном shadowing). Значит бизнес-правила проверяются на
  **тестовой** реализации репозиториев, а боевая dev-реализация проверяется только через HTTP
  (26 тестов, частично). **Тестов репозиториев нет вообще** (ни одного файла `*RepositoryTests.cs`),
  и после Этапа 3 EF-репозитории останутся без какого-либо contract-теста.
- **Contract-тестов против `api-contracts.md` нет**: DTO воспроизведены вручную как `Wire*`
  (`IntegrationApiEndpointsTests.cs:27-138`) — дрейф контракта не виден; ProblemDetails поля
  ассертируются частично (401/403 без тела).
- Покрытие: `coverlet.collector` подключён (`WorkTime.Tests.csproj:13`), но порога покрытия
  нет и метрики не собраны.

## 6. Что признано корректным

- Ровно 25 unit-фактов, имена и ассерты соответствуют заявленным BR (BR1, BR2, BR3, BR4/BR11,
  BR5, BR7, BR8, BR9, BR10, BR12, BR14/BR15/BR16, BR21, BR25, BR26, BR27, BR35/BR36).
- Integration-слой реально ходит по HTTP с настоящими JWT и ассертирует ProblemDetails `code`
  для 409/400/404; happy-path сквозных сценариев (день → перерывы → завершение → daily/monthly) покрыт.
- Изоляция state: новый хост на каждый тест, dispose в `finally`; в dev-репозиториях нет
  статического mutable-state → перекрёстного загрязнения и порядка зависимостей не обнаружено.
- `public partial class Program` → фабрика компилируется без `InternalsVisibleTo`.
- Парольные фикстуры хранят Argon2id-хеш, открытый пароль не пишется (BR34 в фикстурах соблюдён).
- BR32 проверен в обе стороны (истечение после 9 ч и «активность без ошибки продлевает сессию»).
- Dev-сид гейтед окружением и ручным запуском, в тестовые хосты не протекает.
