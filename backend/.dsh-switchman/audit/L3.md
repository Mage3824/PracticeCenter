# Лан L3 — Производительность и масштабируемость (аудит, read-only)

Дата анализа: кодовое состояние этапа 1–2 (in-memory репозитории + API/JWT). Этап 3 (EF Core/MySQL) ещё не начат,
поэтому часть находок — «наследие dev-tier», которое станет узким местом при переходе на БД.

---

## 1. Критические

### 1.1 `monthly-report-n-plus-one-await-loop`
`ReportService.GetMonthlyReportAsync` строит матрицу «сотрудник × день» вложенными циклами с `await` внутри
(`ReportService.cs:224` → `:249` → `:271`).

- `daysOfPeriod` берётся **на всю систему**, без фильтра по отделу/сотруднику (`ReportService.cs:214`), а
  принадлежность дня сотруднику проверяется внутри цикла (`:251` `workDay.UserId != employee.Id`).
- На каждую ячейку матрицы — отдельный `await TrySumCountedBreakTimeAsync(workDay.Id, …)` (`:271`), который
  внутри делает `GetByWorkDayIdAsync` и перебирает весь словарь перерывов (`ReportService.cs:316-323`,
  `DevRepositories.WorkTime.cs:223-236`).
- На каждую ячейку дополнительно `TryHasAbsenceOn(absencesOfPeriod, …)` (`:263`), который линейно перебирает
  **все** отсутствия периода (`ReportService.cs:350-364`).

Сложность: O(E × D_all × B) + O(E × D × A). Для 200 сотрудников × 31 день × 100 перерывов × 300 отсутствий —
порядка 10⁶–10⁷ итераций плюс ~6200 обращений к репозиторию. В EF это станет ~6200 SQL-запросами на один
HTTP-запрос (классический N+1), endpoint `/api/reports/monthly` и его CSV-экспорт (`ReportsController.cs:85`,
`:169-178`) будут деградировать линейно с ростом данных.

Исправление (один проход вместо вложенных await):
```csharp
// 1) дни одного отдела и одного периода, сгруппированные по сотруднику
var daysByUser = (await _workDays.GetFinishedDaysForPeriodAsync(periodStart, periodEnd, ct))
    .GroupBy(d => d.UserId).ToDictionary(g => g.Key, g => g.ToList());
// 2) отсутствия — множеством (userId, day)
var absenceKeys = (await _absences.GetByDateRangeAsync(periodStart, periodEnd, ct))
    .Select(a => (a.UserId, a.Date.Date)).ToHashSet();
// 3) перерывы — один запрос на период, сгруппированный по WorkDayId
var breakMinutesByDay = (await _breaks.GetForWorkDaysAsync(daysByUser.Keys, ct))
    .Where(b => b.Counted).GroupBy(b => b.WorkDayId)
    .ToDictionary(g => g.Key, g => g.Sum(b => (b.Duration ?? b.EndTime!.Value - b.StartTime).TotalMinutes));
```
Нужен новый метод контракта `IBreakRepository.GetForWorkDaysAsync(IEnumerable<Guid>, ct)` (пачечный fetch),
и фильтрация дней по отделу на стороне репозитория.

### 1.2 `sync-over-async-inside-global-locks`
17 мест `.GetAwaiter().GetResult()` — и все они стоят **внутри** `lock`, где `await` запрещён:

- `WorkTimeService.cs:115-126` (`:120` расчёт рабочего времени, `:125` SaveAsync), `:160`, `:163`, `:210`
- `BreakService.cs:128-146` (`:132`, `:136`, `:146`)
- `AbsenceService.cs:56-84` (`:60`, `:69`, `:84`)
- `AuthService.cs:76-81` (`:81`), `:103-139` (`:139`)
- `UsersController.cs:157-177` (`:177`), `:201-205` (`:205`), `:228-233` (`:233`), `:286-300` (`:294`)

Блокировка потока пула потоков во время чужой async-операции при высокой нагрузке даёт thread-pool starvation
(зависание всей апки, а не только этого эндпоинта), а в EF добавит удержание соединения/транзакции на
заблокированном потоке. Комбинирование «глобальный lock + блокирующий wait» означает: один запрос
`FinishWorkDay` занимает тред **и** весь гейт `WorkTime` до конца.

Исправление: убрать `lock` из методов сервиса, а атомарность read-modify-write обеспечить на уровне БД
(транзакция + optimistic concurrency `RowVersion`, либо `FOR UPDATE`), либо клонировать сущность и писать
результат атомарно:
```csharp
// вместо lock + GetResult():
var breaks = await _breaks.GetByWorkDayIdAsync(workDay.Id, cancellationToken);
var worked = SumCounted(breaks);          // чистый sync-расчёт, без async под lock
workDay.EndTime = endTime;
workDay.CountedInReports = worked >= WorkTimeRules.MinDayDuration;
await _workDays.SaveAsync(workDay, cancellationToken); // EF SaveChanges в транзакции
```
Расчёт рабочего времени/перерывов вообще должен стать синхронным (`TimeSpan CalculateWorkedTime(WorkDay, IReadOnlyList<Break>)`),
чтобы блокирующие вызовы исчезли из тела `lock`.

### 1.3 `unguarded-dictionary-singleton-races`
Часть репозиториев — синглтоны с **обычным** `Dictionary`, без `ConcurrentDictionary` и без внешнего lock:

- `DevRepositories.Users.cs:17` (`_users`), `:130` (`_departments`)
- `DevRepositories.Support.cs:11` (`_absences`), `:134` (`_auditLogs`), `:194` (`_closures`)
- `DevRepositories.Reports.cs:11` (`_reports`), `:69` (`_comments`)

Запись идёт из Controller без гейта: `DepartmentsController.cs:91`, `:131`, `:169` (`SaveAsync`/`DeleteAsync`),
`ReportsController.cs:146` (`_comments.SaveAsync`), `AdminController.cs:87`, `:126` (`_periodClosures.SaveAsync`),
тогда как другие параллельные запросы перечисляют тот же словарь (`DevRepositories.Users.cs:48`, `:71`, `:89`,
`DevRepositories.Support.cs:58`, `:78`, `:98`). Одновременный `Add`/`Remove` во время enumerate в
`Dictionary` — это испорченные бакеты, потерю/дублирование записей и известный «бесконечный цикл при rehash»
(CPU 100%, зависание процесса). Гейты `EntityMutationGates` покрывают только три из семи сущностей.

Исправление: `ConcurrentDictionary` во всех репозиториях dev-tier (как уже сделано для WorkDay/Break,
`DevRepositories.WorkTime.cs:16`, `:189`), либо один внутренний lock на репозиторий; при переходе на EF —
сохранение через `SaveChangesAsync` с `ConcurrencyToken`.

### 1.4 `in-memory-state-blocks-horizontal-scaling`
Весь «стейт» живёт в синглтонах одного процесса: репозитории (`Program.cs:53-61`), `UserActivityTracker`
(`Program.cs:93-94`, `Middleware.cs:152-200`). За load-balancer без sticky sessions:

- BR32 (таймаут сессии 8 ч) считается на каждом инстансе отдельно: запросы пользователя, попавшие на
  второй инстанс, не видят активность с первого → сессия «никогда не истекает» на одном инстансе и
  «истекает раньше срока» на другом (`Middleware.cs:170-175`, запись `:270`).
- Гейт BR20 («нельзя убрать последнего активного администратора») защищён process-wide мьютексом
  (`EntityMutationGates.cs:6`, `UsersController.cs:294`) — два инстанса пропускают две параллельные
  деактивации и оставляют систему без администратора.
- `DevSeed` выполняется на каждом инстансе независимо (`Program.cs:171-177`): N копий демо-данных,
  расхождение данных между инстансами.
- `IDistributedCache`/Redis нигде не зарегистрированы (поиск по `src/WorkTime.Api` не дал ни одного
  `AddMemoryCache`/`IDistributedCache`/`UseResponseCompression`).

Исправление: состояние → в MySQL (активность/локаут в таблице `user_sessions`, `users.failed_attempts`,
`users.locked_until`) или в Redis через `IDistributedCache` с атомарными Lua-операциями; проверка
«последний администратор» — SQL-запрос в транзакции (`SELECT COUNT(*) … FOR UPDATE`), а не lock;
сидирование — только миграция/один инстанс (или отдельная job-инстанс).

## 2. Высокие

### 2.1 `process-wide-mutation-mutex-serializes-throughput`
`EntityMutationGates.Users/WorkTime/Absences` — статические мьютексы на весь процесс
(`EntityMutationGates.cs:4-9`), `UserMutationLock.SyncRoot` — тот же объект (`:14-17`). Все `StartWorkDay`,
`FinishWorkDay`, `StartBreak`, `FinishBreak`, `SetAbsence`, `Login`, создание/правка/деактивация пользователей
серилизуются на трёх глобальных замках: пропускная способность эндпоинтов упирается в один поток, а
очередь на замке при пике даёт лавинообразное время ответа. Кроме того, это защита только внутри процесса —
на 2+ инстансах она ничего не защищает.

Исправление: гейт на уровне ключа сущности (`ConcurrentDictionary<Guid, SemaphoreSlim>`), а при переходе на
EF — транзакция с `Serializable`/`FOR UPDATE` или оптимистичная конкуренция; `lock` из Application-сервисов убрать.

### 2.2 `cancellation-token-never-honored`
Контракт репозиториев корректно declares `CancellationToken` везде (`IRepositories.cs:12-33` и далее), но ни
одна реализация его не использует: 90 сигнатур в `src/WorkTime.Infrastructure` и ноль обращений к токену
(нет `ThrowIfCancellationRequested`/`IsCancellationRequested`, `DevRepositories.Users.cs:19-23`,
`DevRepositories.Support.cs:21-24`, `DevRepositories.Reports.cs:13-16`). Аналогично сервисы только
транзитивно передают его. `RequestContext.TryStopSignal()` существует (`RequestContext.cs`), но downstream
ничего не прерывает. При отмене клиентом запроса тяжёлый месячный отчёт продолжает работать и держать
ресурсы; в EF отсутствие токена в `FromSqlAsync`/`SaveChangesAsync` означает «запрос в MySQL не отменяется».

Исправление: в EF-репозиториях передавать `cancellationToken` во `ToListAsync(ct)`/`SaveChangesAsync(ct)`;
в dev-tier — минимально `cancellationToken.ThrowIfCancellationRequested()` в начало каждого скана, чтобы
контракт был честным уже сейчас.

### 2.3 `audit-log-unbounded-and-no-paging`
`InMemoryAuditLogRepository` — словарь без eviction (`DevRepositories.Support.cs:134`), записи добавляются на
каждое критическое действие (`ManagementWires.cs:225`, `DepartmentsController.cs:92`, `UsersController.cs:112`,
`AdminController.cs:88`, `WorkTimeService.cs:178`). API отдаёт всю историю сущности без фильтра и без страниц
(`AdminController.cs:55` `GetHistoryForEntityAsync`, скан всего словаря `:166`). Память процесса растёт
монотонно с числом действий; ответ API растёт без границ (для сущности с тысячами правок — мегабайты JSON).
После этапа 4 (BR29/BR30) это же станет таблицей без ретенции.

Исправление: метод контракта с пагинацией `GetHistoryForEntityAsync(entityId, ct, page, pageSize)` (или
`since`/`take`), ограничение ретенции ( purgeolder than N дней / partition по дате), и индекс по
`(entity_id, timestamp)` в EF-схеме.

### 2.4 `console-logging-no-correlation-no-metrics`
Логирование — только встроенный `ILogger` + Console (`Program.cs:47-49`), уровни из `appsettings.json:8-20`
(Default=Information). Каждый запрос пишется в консоль (`Middleware.cs:291-296`), Console-провайдер
 сериализует запись через внутренний lock → на high RPS это узкое место и источник contention. Нет
correlation/activity id, нет структурированных событий, нет метрик (duration есть только как текст сообщения
`:296`), нет Serilog/OpenTelemetry.

Исправление: Serilog с `Seq`/файлом и `LogEvent.Properties` (userId, entityId, rule code), `Activity`/
`TraceIdentifier` как correlation id в начале pipeline, `UseResponseCompression`; метрики —
OpenTelemetry ASP.NET metrics (request duration histogram) либо `System.Diagnostics.Metrics`; для
request-log уровень `Debug` вместо `Information`, чтобы не писать каждый 2xx.

## 3. Средние

### 3.1 `csv-export-quadratic-day-keys`
Сбор уникальных дней месячного отчёта делает линейный `List.Contains` во вложенном цикле
(`ManagementWires.cs:152-162`): O(R×D × R×D) сравнений строк. Для 200 строк × 31 день это ~38M
сравнений; плюс весь CSV собирается как одна строка и конвертируется в `byte[]` (`:166-186`), т.е.
двойная аллокация полного текста, и контроллер пишет его целиком
(`ReportsController.cs:178`). BR17 требует Excel — если экспорт станет потоковым, текущая схема не
масштабируется.

Исправление: `HashSet<string>`/`SortedSet<string>` для dayKeys; писать экспорт напрямую в
`HttpResponse.WriteAsync`/`Response.Body` потоково (`StreamWriter` + `IAsyncEnumerable`), без
промежуточного `string` и `byte[]`.

### 3.2 `mixed-now-and-utcnow-timestamps`
Разные базы времени в одном домене: `DateTime.Now` — `AuthService.cs:57` (окно локаута BR35),
`ReportService.cs:98`, `:116` (CreatedAt/UpdatedAt), `WorkTimeService.cs:175` (audit Timestamp);
`DateTime.UtcNow` — `TokenService.cs:30`, `Middleware.cs:234`, `:270`, `:287`, `AdminController.cs:84`,
`ManagementWires.cs:222`, `AuthController.cs:71`, `WorkDaysController.cs:95`. Следствия: аудит-история
смешает локальные и UTC-метки (невозкорректная сортировка истории, BR29/BR30), окна локаута и сравнение
с `LockedUntil` «плывут» при смене часового пояса/DST сервера, а сессия BR32 считается по UTC против
локальных меток.

Исправление: единый `IClock` (или статический `Clock.UtcNow`) и `DateTime` с `Kind=Utc` во всех
сущностях и метках; в EF хранить UTC; `Kind` проверять при сравнении.

### 3.3 `enum-getvalues-per-request`
`Identity.TryRole` на каждый аутентифицированный запрос выделяет массив `Enum.GetValues<UserRole>()`
и делает `role.ToString()` на每个 элемент (`Identity.cs:42-48`). Это вызывается из
`RequestIdentity.TryRequireKnownUserAsync` почти во всех контроллерах (`UsersController.cs:74`,
`DepartmentsController.cs:74`, `WorkDaysController.cs:55`, `ReportsController.cs:54` и т.д.), т.е.
несколько аллокаций + N строковых сравнений на запрос.

Исправление:
```csharp
if (Enum.TryParse<UserRole>(roleName, ignoreCase: false, out var role)) return role;
```
(или кэшированный `static readonly string[] RoleNames`, сравнение по `Ordinal`).

### 3.4 `existence-checks-materialize-collections`
Проверки «есть ли дети/сотрудники» материализуют полные списки, чтобы потом бросить исключение на первом
элементе: `DepartmentsController.cs:153-159`, `:161-167` (`foreach (var unused …)`). Репозиторий при этом
сканирует весь словарь и строит List/Dictionary (`DevRepositories.Users.cs:85-107`,
`DevRepositories.Users.cs:111` `new List<User>(_users.Values)`). Это лишние аллокации и O(N) на каждый
запрос deletion/list.

Исправление: метод контракта `Task<bool> HasChildrenAsync(Guid departmentId, ct)` /
`CountActiveEmployeesAsync(Guid, ct)`; в EF — `AnyAsync`/`CountAsync` вместо материализации.

### 3.5 `duplicate-repository-reads-per-request`
Один и тот же пользователь читается дважды за запрос: `AbsencesController.cs:49`
(`TryRequireKnownUserAsync(_users, actorId)`) затем `AbsenceService.cs:35`
(`_users.GetByIdAsync(actorId)`); аналогично `AbsencesController.cs:71` + `AbsenceService.cs:35`;
`WorkDaysController.cs:91` + сервисные проверки. И один метод сервиса делает несколько последовательных
обращений там, где достаточно одного: `AbsenceService.cs:106` (user), `:112` (closure), `:115`
(absences по closure), `:131` (absences по date) — два независимых скана отсутствий для одного дня
(`Support.cs:74-100`, `:93-100`).

Исправление: кэшировать субъект запроса в `HttpContext.Items`/`RequestContextProvider` (один fetch на
запрос) и добавить `IAbsenceRepository.GetForEmployeeOnDateAsync`- overload, возвращающий и блокирующие,
и «на день» данные одним сканом; в EF — одна read-транзакция/один join.

### 3.6 `wire-mapping-double-copy-no-pagination`
Wire-конвертеры собирают `List` и затем `ToArray()` — двойная копия каждого элемента массива
(`Wire.cs:332-341`, `:369`, `:435`, `:460`; `ManagementWires.cs:80`, `:100`), а list-эндпоинты вообще
без пагинации: `UsersController.cs:46` отдаёт всех пользователей, `DepartmentsController.cs:39` — все
отделы, `AbsencesController.cs:110-118` — весь диапазон дат, `ReportsController.cs:85` — полную матрицу.
Ответы и аллокации растут без границ с объёмом данных.

Исправление: возвращать массив прямо из LINQ (`Select(...).ToArray()` или `List<T>` без второго
`ToArray()`); добавить параметры `page`/`pageSize` (или `take`/`skip`) в GET-контракты и в репозитории,
с ограничением по умолчанию (например 200 строк).

## 4. Проверено и признано корректным (clean areas)

- Контракты репозиториев полностью асинхронные и с `CancellationToken` в каждой сигнатуре
  (`IRepositories.cs:10-33` и далее) — архитектурная база для EF-этапа правильная.
- Middleware-пайплайн асинхронный, записи ответа идут с `RequestAborted`
  (`Middleware.cs:102`, `:258`); блокирующих вызовов в middleware нет.
- `Thread.Sleep`/`Task.Delay`/блокирующих sync-методов в сервисе и API нет — блокировка встречается только
  как `GetAwaiter().GetResult()` (см. 1.2).
- WorkDay/Break репозитории уже используют `ConcurrentDictionary` (`DevRepositories.WorkTime.cs:16`, `:189`)
  — эталон для остальных репозиториев.
- Argon2 параметры умеренные и зафиксированы в PHC-строке: `m=19456 KiB, t=2, p=1`
  (`PasswordHasher.cs:12-14`) — ~19 MiB и 2 прохода на verification, т.е. CPU-стоимость только на login,
  не на каждый запрос; параметры проверяются по диапазону (`:68-69`).
- JWT — stateless (HS256, `TokenService.cs:30-40`), т.е. сама авторизация масштабируется горизонтально;
  узкое место — не токен, а локальный activity-трекер (см. 1.4).
- `Task.FromResult` для синхронных in-memory путей (`DevRepositories.Users.cs:22`, `:39`, `Support.cs:24`)
  не добавляет лишний hop через пул потоков.
- `DevSeed` выполняется только в Development и только при ручном запуске
  (`Program.cs:171-177`, `DevSeed.cs:42` проверка «уже есть пользователи») — нет лишней работы на старте
  production.
- `UserActivityTracker` ограничен по объёму: prune удаляет записи старше окна BR32 и выполняется не чаще
  раза в окно (`Middleware.cs:185-200`) — утечки нет, но prune под global lock на каждый запрос (см. 2.1).
- Замер длительности запроса дешёвый и не аллоцирует объектов сверх сообщения лога
  (`Middleware.cs:287-296`).
- Конкатенация строк в горячих местах использует `StringBuilder`, а не `+=` в цикле
  (`ManagementWires.cs:166-186`); `+=` встречается только на `TimeSpan`-аккумуляторы
  (`WorkTimeService.cs:235`, `BreakService.cs:175`, `ReportService.cs:330`) — это не аллокация текста.
