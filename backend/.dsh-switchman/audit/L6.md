## 1. DI: singletons репозиториев против scoped DbContext (Critical)

`src/WorkTime.Api/Program.cs:53-61` — все 9 репозиториев зарегистрированы `AddSingleton<IXxxRepository, InMemoryXxxRepository>()`; сервисы — `AddScoped` (`Program.cs:64-68`, `TokenService` :71, `RequestContextProvider` :76). Scoped сервисы держат ссылки на singleton-репозитории, т.е. одно хранилище живёт весь процесс и разделяется между запросами.

Для EF это неработоспособно: `DbContext` не thread-safe и должен жить на запрос.
- Правильная регистрация: `builder.Services.AddDbContext<ApplicationDbContext>(o => o.UseMySql(cs, ServerVersion.AutoDetect(cs)))` + репозитории `AddScoped`. Либо `AddDbContextFactory`, если нужен `IDbContextFactory` для фоновых сервисов Этапа 4 (AutoFinish 23:59:59, бэкап 03:00) и для `EnableRetryOnFailure`.
- `EnableRetryOnFailure` не работает с пользовательскими транзакциями: внутри `IDbContextTransaction` стратегия retries не применяется → транзакции обёртывать вручную (`ExecutionStrategy.Execute`).
- Сид в `Program.cs:174-175` берёт `GetRequiredService<IUserRepository>()` из root provider → с scoped репозиторием это исключение (или создание DbContext вне запроса). Сид должен стать отдельным инициализатором после `MigrateAsync` (см. п. 11).

## 2. Глобальные мьютексы + sync-over-async + потеря CancellationToken (Critical)

`src/WorkTime.Application/EntityMutationGates.cs:4-9` (`Users`, `WorkTime`, `Absences`) и `:14-17` (`UserMutationLock.SyncRoot`, открыт для API) — гейты созданы потому, что in-memory репозитории хранят общие объекты в singleton (`src/WorkTime.Infrastructure/DevRepositories.Users.cs:17`, `DevRepositories.Support.cs:11,134,194`, `DevRepositories.Reports.cs:11,69`; только WorkDay/Break используют `ConcurrentDictionary` — `DevRepositories.WorkTime.cs:16,192`).

Места правки под lock с `.GetAwaiter().GetResult()`:
- `Services/WorkTimeService.cs:115-125` (FinishWorkDay), `:154-163` (AutoFinish), `:194-210` (закрытие перерывов)
- `Services/AbsenceService.cs:56-69` и `:84`
- `Services/AuthService.cs:76-81` (сброс счётчика), `:103-139` (инкремент + блокировка)
- API: `Controllers/UsersController.cs:177, 205, 233, 294`

Что ломается на EF:
1. `lock` сериализует несвязанные запросы (все пользователи мира ждут друг друга на FinishWorkDay) — на БД это не нужно вовсе.
2. sync-over-async теряет `cancellationToken`: вызов идёт без токена, EF-запрос выполняется до конца даже при abort (BR32 timeout не сработает).
3. В scoped DbContext повторный `GetByIdAsync` возвращает тот же tracked-экземпляр → «изменили и SaveAsync» превращается в implicit update; второй `SaveAsync` с другим объектом того же id вызовет conflict tracking.
4. Блокирование threads пула Kestrel при БД-IO — деградация под нагрузкой.

Фикс: убрать гейты после перехода на EF; вместо read-modify-write — целенаправленные методы репозитория (`MarkDayFinishedAsync(id, end, counted, ct)`, `IncrementFailedAttemptsAsync(id, ct)`), всё async, токен пробрасывается в `QueryAsync`/`ExecuteAsync`.

## 4. Счётчик неудачных логинов (BR35) — нужен атомарный UPDATE (High)

`Services/AuthService.cs:103-139`: `user.FailedLoginAttempts = user.FailedLoginAttempts + 1` под process-wide lock, затем `_users.SaveAsync(...)` (:139). На БД два параллельных логина теряют инкремент (lost update). Фикс:
```csharp
await _dbContext.Users
    .Where(u => u.Id == id)
    .ExecuteUpdate(s => s.SetProperty(u => u.FailedLoginAttempts, u => u.FailedLoginAttempts + 1));
// затем перечитать строку (или ExecuteUpdate с условием порога в том же UPDATE)
```

## 8. DateTime.Date и TimeSpan не переводятся в SQL на Pomelo (High)

`Entities.cs:32-35` (`DateTime Date`, `TimeSpan StartTime`, `TimeSpan? EndTime`), `:48-51` (`TimeSpan? Duration`). Сравнения периода сделаны через `.Date` (`DevRepositories.WorkTime.cs:178-182`, `DevRepositories.Support.cs:123`). В LINQ-to-SQL EF Core 8 на MySQL `DateTime.Date`, `TimeSpan`-арифметика (`EndTime - StartTime`) и `ToLower().Contains` не транслируются → InvalidOperationException (client evaluation unsupported). Агрегации сейчас считаются в памяти: `ReportService.cs:166`, `:181-190`, `:257-270`, `:316-336` — на БД это выгружает весь период в память.

Фикс:
- дата дня → колонка `DATE`, тип в C# `DateOnly` (EF Core 8 + Pomelo поддерживают `DateOnly`) или `DateTime` с сравнением `d >= start && d < end.AddDays(1)`;
- время/длительность → `int` минуты (`start_minute`, `end_minute`, `duration_minutes`) либо `TIME(2)`; суммы через `SUM` в SQL (`ExecuteScalarAsync` / `GroupBy` по int), а не `TimeSpan` в LINQ.

## 9. Смешанные DateTime.Now / UtcNow и часовые пояса (High)

`DateTime.Now`: `Services/AuthService.cs:57` (сравнение блокировки), `Services/WorkTimeService.cs:175` (AuditLog.Timestamp), `Services/ReportService.cs:98` (CreatedAt), `:116` (UpdatedAt).

MySQL `DATETIME` без TZ; Pomelo сохраняет значения «как есть», `Kind=Unspecified`. Один логин сравнивает локальное время сервера (MSK) с `LockedUntil`, записанным из `DateTime.Now`, а соседние поля пишутся в UTC → BR35 «до конца дня» и BR23 ClosedAt расходятся на 3 часа и на DST.

Фикс: единый `IClock` (Application) с `UtcNow`, `DateTime.SpecifyKind(..., DateTimeKind.Utc)` перед записью, и решение о хранении: `DateTimeOffset` → Pomelo `DATETIME(6)` в UTC, либо `DATETIME(3)` + соглашение «всё в UTC». BR3 (23:59:59) и BR33 (03:00) — локальные календарные времена: хранить расчёт в TZ клиента и конвертировать явно.

## 14. Имена в MySQL: reserved words, casing, collation (Medium)

Таблицы по имени сущности: `User`, `Report`, `Comment`, `Break` (`Entities.cs:7,54,63,44`). `USER` — функция MySQL, `BREAK`/`REPORT` небезопасны в неэкранированных запросах; Pomelo экранирует идентификаторы, но сырые SQL/миграции и `ExecuteSqlRaw` без backticks ломаются.
