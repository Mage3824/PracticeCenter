## 1. JWT — точные значения из кода

### Подпись и ключ
- Алгоритм: `SecurityAlgorithms.HmacSha256` (HS256) — `src/WorkTime.Api/TokenService.cs:35`.
- Ключ HMAC: `SHA256.HashData(UTF8.GetBytes(_settings.SecretKey))`, 32 байта — `src/WorkTime.Api/TokenService.cs:33-34`; при валидации тот же алгоритм derivation — `src/WorkTime.Api/TokenService.cs:77-78` (`JwtBearerSetup.TryConfigure`). То есть подписывающий ключ = SHA-256 от строки `JwtSettings.SecretKey`, сам секрет в токен не попадает.
- Валидация длины секрета: `MinSecretKeyBytes = 32` по байтам UTF-8 исходной строки — `src/WorkTime.Api/JwtSettings.cs:26,83`.
- Источник ключа: `appsettings.json`, секция `JwtSettings` — `src/WorkTime.Api/appsettings.json:2-7`:
  `SecretKey = "work-time-development-signing-key-change-me-please-32+-bytes"`, `Issuer = "WorkTime.Api"`, `Audience = "WorkTime.Client"`, `ExpiryMinutes = 480`.
  Файл лежит в репозитории, т.е. ключ коммитится; отдельного `appsettings.Production.json` и переменных окружения нет.
- Development-дефолт продублирован в коде: `JwtSettings.DefaultDevelopmentSecretKey` — `src/WorkTime.Api/JwtSettings.cs:10-11`, подставляется при пустом значении вне Development (`JwtSettings.cs:52-64`).
  `ValidateSettings` (`JwtSettings.cs:74-95`) проверяет только пустоту, длину ≥32 байт, непустые Issuer/Audience и `ExpiryMinutes > 0` — совпадение строки с development-ключем вне Development НЕ проверяется.

### Claims
`src/WorkTime.Api/TokenService.cs:37-42`: `ClaimTypes.NameIdentifier` = `userId.ToString()` (Guid пользователя), `ClaimTypes.Role` = `role.ToString()` (`Admin`/`Manager`/`Employee` — имена enum `UserRole`), `ClaimTypes.Name` = login. Никаких `jti`, `nbf`, nonce, fingerprint-привязки к клиенту нет (`IssuedAt`/`Expires` есть, `TokenService.cs:49-50`).

### Срок жизни и валидация
- `Expires = IssuedAt + ExpiryMinutes` = 480 минут = 8 ч (БП32) — `TokenService.cs:31`; `expiresIn` в ответе логина — `TokenService.cs:60-63`, `AuthController.cs:74`.
- `TokenValidationParameters` (`src/WorkTime.Api/TokenService.cs:80-92`): `ValidateIssuer = true` (`ValidIssuer = settings.Issuer`), `ValidateAudience = true` (`ValidAudience = settings.Audience`), `ValidateLifetime = true`, `ValidateIssuerSigningKey = true`, `IssuerSigningKey = SHA256(secret)`, `ClockSkew = TimeSpan.FromMinutes(1)` (`JwtBearerSetup.ClockSkew`, строка 71), `NameClaimType = ClaimTypes.Name`, `RoleClaimType = ClaimTypes.Role`.
- Совпадение имён claims: политики строятся через `RolesAuthorizationRequirement` (`src/WorkTime.Api/AuthorizationPolicies.cs:44-50`), который читает `RoleClaimType`; токен пишет `ClaimTypes.Role` → совпадает, `User.IsInRole("Manager"/"Admin")` в контроллерах тоже работает (`AbsencesController.cs:91`).
- Схема аутентификации: `AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer(...)` — `src/WorkTime.Api/Program.cs:79-81`; порядок конвейера: exception handler → request logging → Swagger → authentication → BR32 → authorization — `Program.cs:180-191`.
- Replay/отзыв: отзываемости нет — ни `jti`, ни revocation-хранилища, ни logout-эндпоинта (в `src/WorkTime.Api` нет ни `logout`, ни `signout`). Захваченный токен воспроизводим до истечения 8 ч.

## 2. Политики и соответствие контрактам

`AuthorizationPolicies.cs:27-32`: `DefaultPolicy` и `FallbackPolicy` = `DenyAnonymousAuthorizationRequirement`; `AdminOnly` = роли `["Admin"]`, `ManagerOrAdmin` = `["Manager","Admin"]`, `EmployeeOnly` = `["Employee"]` (плюс `DenyAnonymous`, строки 46-49).
Анонимный только `POST /api/auth/login` (`[AllowAnonymous]`, `Controllers/AuthController.cs:40-41`); классы контроллеров WorkDays/Breaks/Reports/Absences имеют `[Authorize]` на уровне класса (`WorkDaysController.cs:16`, `BreaksController.cs:14`, `ReportsController.cs:16`, `AbsencesController.cs:16`), т.е. без политики = DefaultPolicy (аутентифицированный любой роли).

Соответствие ролям (БП19..БП28, БП17):
- Корректно: `GET /api/audit-logs` и period-closures close/reopen — `AdminController.cs:16` (`AdminOnly`) + БП29 «логи доступны только администратору»; создание/изменение/удаление/деактивация/unlock пользователей и отделов — `AdminOnly` (`UsersController.cs:65,119,187,214,249`, `DepartmentsController.cs:66,100,140`); списки пользователей/отделов и месячный отчёт/комментарии/экспорт — `ManagerOrAdmin` (`UsersController.cs:36,54`, `DepartmentsController.cs:34,43,54`, `ReportsController.cs:76,111,151,162,185`), что соответствует БП17 и БП22; проставление/изменение отсутствия — `ManagerOrAdmin` (`AbsencesController.cs:39,61,101`) = БП25/БП28; чтение отсутствий — БП27 с гейтом по субъекту (`AbsencesController.cs:89-94`: сотрудник только свой id, иначе 403).
- Идентичность всегда из токена (`RequestIdentity.TrySubjectUserId`, `Identity.cs:13-15`), id пользователя никогда не берётся из тела: `WorkDaysController.cs:51,72,89,121`, `BreaksController.cs:41,61`, `ReportsController.cs:52,101,120`; `can-start` для чужого employeeId отсекается на `WorkDaysController.cs:141`.
- Единственное расхождение по ролям: редактирование текстового отчёта чужого сотрудника (см. находку 8). Месячный отчёт по произвольному `departmentId` (в т.ч. `Guid.Empty` → «все активные пользователи системы», `ReportService.cs:194-195,220`) допустим по БП22 («Руководитель: просмотр отчетов всех сотрудников»), поэтому не считается нарушением.

## 3. Middleware.cs (БП32)

- `UserActivityTracker` (`src/WorkTime.Api/Middleware.cs:152-205`): singleton (`Program.cs:93-94`), поле `ConcurrentDictionary<string, DateTime> _lastActivity`, ключ — строка Guid из `ClaimTypes.NameIdentifier`, лимит `TimeSpan.FromMinutes(settings.ExpiryMinutes)` = 8 ч (строки 154-163).
- Потокобезопасность: запись через indexer `ConcurrentDictionary` (`Middleware.cs:180`) — атомарно, последний write выигрывает; prune под `_pruneLock` (185-204),扫 по `ConcurrentDictionary` безопасен.
- Очистка/память: prune выполняется внутри `TryRecordActivity`, не чаще одного раза в `_limit` (189-192) и удаляет записи старше `_limit` (196-202). Размер словаря ограничен ~8 часами активных субъектов — утечки нет, но очистка идёт только при активном трафике.
- Сравнение с `exp` токена: трекер не читает `exp`; он сравнивает `now - lastActivity > _limit` (175), а `_limit` = срок жизни токена, поэтому БП32 и срок токена совпадают; `ClockSkew` 1 мин (TokenService.cs:71) допускает токен на минуту дольше, но трекер всё равно отказывает после 8 ч неактивности.
- Поведение после logout: logout отсутствует; запись активности НЕ удаляется при выходе и НЕ удаляется при деактивации/удалении пользователя, так что «сессия» формально живёт до истечения токена. У ушедшего пользователя запись остаётся до prune.
- Обход middleware: `UserActivityTimeoutMiddleware` стоит после `UseAuthentication` и до `UseAuthorization` (`Program.cs:186-191`), значит анонимные эндпоинты (`/api/auth/login`) и Swagger (`Program.cs:183-184`, до аутентификации) его не проходят — корректно для login, но Swagger доступен анонимно и в Production (см. находку 2).
- Корректность 401 при >8 ч: при просрочке возвращается 401 + `WWW-Authenticate: Bearer` + ProblemDetails `SESSION_EXPIRED` (`Middleware.cs:236-259`); активность продлевается в `finally` любым аутентифицированным запросом (264-271), успешный login сбрасывает baseline (`AuthController.cs:69-71`).
- Ключевой дефект: отсутствие записи трактуется как «не просрочено» (`Middleware.cs:168-173`), а prune удаляет именно просроченные записи → токен idle-пользователя возвращается в строй (находка 6).

## 4. PasswordHasher.cs (Argon2id)

- Версия и формат: `$argon2id$v=19$m=...,t=...,p=...$salt$hash` (PHC), `src/WorkTime.Application/PasswordHasher.cs:30-32`; base64 соли и хеша без padding (`TrimEnd('=')`), при сверке padding восстанавливается (`PadBase64`, 114-122).
- Параметры签发: `SaltSize = 16` (128 бит), `HashSize = 32` (256 бит), `MemorySize = 19456` KiB (≈19 MiB), `Iterations = 2` (t), `Parallelism = 1` (p) — строки 10-14; это OWASP-минимум (m=19456, t=2, p=1).
- Соль: `RandomNumberGenerator.GetBytes(SaltSize)` на каждый `TryHash` — криптографически случайная, уникальная, не переиспользуется (`PasswordHasher.cs:27`).
- Хеш: `Argon2id.GetBytes(HashSize)` = 32 байта (111); `using var argon2` корректноdispose'ится.
- Сравнение: `CryptographicOperations.FixedTimeEquals(actualHash, expectedHash)` (`PasswordHasher.cs:91`) — constant-time, не `==`.
- null/пустой пароль: внутри `HashPassword` `password ?? string.Empty` (`PasswordHasher.cs:103`), т.е. null не бросает `ArgumentNullException`; `TryVerify` на null/пустой/битый storedHash: `Split('$')` даёт length != 6 → false (41-44), любое исключение → false (93-97).
- Защита от DoS на чужой PHC-строке: верхние границы `MaxMemoryKiB = 65536`, `MaxIterations = 10`, `MaxParallelism = 16`, соль 8..64 байт, хеш 16..64 байт (17-23, 67-72, 82-86).
- Вызов: проверка пароля `PasswordHasher.TryVerify(password, user.PasswordHash)` — `src/WorkTime.Application/Services/AuthService.cs:156`; хеш при создании пользователя `UsersController.cs:101`, в сиде `DevSeed.cs:70`. Открытый пароль не хранится и наружу не отдаётся (`ManagementWires.cs:3`, `UsersController.cs:3`).

BR32 пишет в лог Guid пользователя + лимит (238-239).

- Model-state (валидация DataAnnotations): `InvalidModelStateResponseFactory` (`Program.cs:98-137`) собирает `entry.Key + ": " + error.ErrorMessage` и кладёт в `detail`. Дефолные сообщения DataAnnotations для `[RegularExpression]`/`[Range]` содержат подставленное значение; в `Requests.cs` дата/время имеют кастомные сообщения без значения (`RequestPatterns.DateErrorMessage`, `TimeOfDayErrorMessage`, строки 22-24), но поля без `ErrorMessage` эхо-значение. Риск низкий, но есть (находка 12).
- `DevSeed.cs:22-28` — константы `admin`/`manager`/`employee` и пароли `admin-password-1`/`manager-password-1`/`employee-password-1` в коде (коммитятся); сид запускается только в Development и только при ручном запуске (`Program.cs:171-177`), в прод не попадает.
- Audit-лог содержит PII (`login=..., role=..., departmentId=..., isActive=...`, `UsersController.cs:312-316`) — это intended по БП29/БП30, читают только `AdminOnly` (`AdminController.cs:16`).
- Swagger анонимный и в Production: `app.UseSwagger()` + `UseSwaggerUI` без env-гейта (`Program.cs:183-184`); Bearer-схема описана, требование добавляется только не-`AllowAnonymous` операциям (`Program.cs:140-161`, фильтр 207-220).

## 6. Rate limiting / CORS / TLS / лимиты / enumeration

- Нет `AddRateLimiter`/`UseRateLimiter` (ни в `Program.cs`, ни в csproj), нет `AddCors`/`UseCors`, нет `UseHttpsRedirection`, нет `UseHsts`, нет CSP/заголовков безопасности, нет `ForwardedHeaders`, нет `MaxRequestBodySize`/`FormOptions` (дефолт Kestrel ~30 МБ). `AllowedHosts: "*"` (`appsettings.json:21`) при отсутствии Host Filtering middleware ничего не ограничивает.
- `/api/auth/login` — единственный анонимный эндпоинт (`AuthController.cs:40-41`), без лимита попыток; каждый промах стоит 19 MiB и 2 итерации Argon2 (`PasswordHasher.cs:12-13`) → усилитель CPU/RAM под flood.
- БП35 статус: константы `WrongPasswordsToLock = 5` (`AuthService.cs:22`), `LockDuration = 15 минут` (24), `WorkTimeRules.MaxFailedAttempts = 10` (`src/WorkTime.Domain/WorkTimeRules.cs:12`), `WorkTimeRules.CaptchaThreshold = 2` (`WorkTimeRules.cs:14`); лок пишется в `user.LockedUntil` (109-123), счётчик `FailedLoginAttempts` сохраняется (139). Но гейт `lockRulesApply = user.Role == Admin || Manager` (`AuthService.cs:107`) отключает и лок, и капчу для роли Employee — БП35/БП36 (business_rules.md:66-67) роль не ограничивают.
- БП36 статус: `RequiresCaptcha` только флаг в ответе (`AuthService.cs:127-132`, `Wire.cs:22`), `LoginRequest` не имеет поля капчи и сервер её не проверяет (`Requests.cs:27-33`) → правило обходится молча.
- User enumeration: неизвестный login → `[RU] No account with this login.` (`AuthService.cs:34-41`), неверный пароль → `[RU] Wrong password.` (136); оба ответа HTTP 200 (`AuthController.cs:55-57`), различие только в сообщении/флагах → подтверждение существования аккаунта.
- Деактивированный пользователь: логин блокируется (`AuthService.cs:45-55`, БП24), но ранее выданный токен остаётся валидным и политики его пропускают (роль берётся из claims) — доступ до 8 ч.
- Токен в query string: нет — export эндпоинты принимают только `periodClosureId`/`departmentId` (`ReportsController.cs:164`), авторизация через header (`Program.cs:156-157`); `accessToken` отдаётся в теле ответа логина (`Wire.cs:30`).
- Sync-over-async на пути логина: `_users.SaveAsync(user, ct).GetAwaiter().GetResult()` (`AuthService.cs:139`) — блокирует поток на каждый промах.

1. Critical: development-подписывающий ключ в `appsettings.json` и не проверяется его совпадение вне Development → в Production токены подписываются ключом из git, любой может выписать себе `Admin`-JWT.
2. High: Swagger UI анонимен и в Production.
3. High: нет rate limiting вообще + тяжёлый KDF на каждый промах логина.
4. High: БП35/БП36 не применяются к роли Employee.
5. High: капча БП36 не проверяется сервером (только флаг).
6. High: обход БП32 — отсутствие записи в трекере трактуется как «не просрочено», prune удаляет просроченные записи, idle-токен воскрешается.
7. High: токен не отзываема; деактивация/смена роли не инвалидирует выданный токен (роль и IsActive берётся из claims).
8. High: руководитель правит чужой текстовый отчёт (БП22 разрешает только комментарии).
9. Medium: enumeration аккаунтов (разные сообщения при неизвестном login и неверном пароле).
10. Medium: sync-over-async на логине → starvation под flood.
11. Medium: политика пароля отсутствует (только `[Required]`, без Min/MaxLength и strength).
12. Medium: model-state detail эхо-значения полей без кастомного ErrorMessage.
13. Low: нет HTTPS redirect/HSTS/CSP/CORS и лимита тела запроса.
14. Low: dev-учётные данные в репозитории (`DevSeed.cs`), Development-only.

## Проверено и признано корректным

- Все флаги валидации JWT включены (`ValidateIssuer/Audience/Lifetime/IssuerSigningKey`), Issuer/Audience точные, `ClockSkew` = 1 мин; derivation ключа идентичен на签发 и валидации (`TokenService.cs:33-34` vs `77-78`).
- `NameClaimType`/`RoleClaimType` = `ClaimTypes.Name`/`ClaimTypes.Role` — совпадают с claims токена и с `RolesAuthorizationRequirement`/`User.IsInRole`.
- `DefaultPolicy` и `FallbackPolicy` = `DenyAnonymousAuthorizationRequirement` → эндпоинт без политики закрыт анониму; анонимен только login.
- Идентичность всегда из субъекта токена, никогда из тела; `can-start` и чтение отсутствий для чужого employeeId отказывают (`WorkDaysController.cs:141`, `AbsencesController.cs:91`); daily-отчёт по чужому employeeId отказывает (`ReportService.cs:145`); редактирование отчёта после закрытия дня — только Admin (`ReportService.cs:107`, БП12).
- Пароли: Argon2id v=19, m=19456 KiB, t=2, p=1, соль 16 байт CSPRNG на каждый hash, hash 32 байта, PHC-строка, сравнение `FixedTimeEquals`, границы параметров против DoS на чужой строке, null-пароль не бросает исключение; открытый пароль и `PasswordHash` наружу не отдаются.
- 500 отдаёт generic `INTERNAL_ERROR` без stacktrace и внутреннего сообщения (`Middleware.cs:80-91`); ProblemDetails + envelope `error{code,message,httpStatus}` (`Middleware.cs:107-131`); 401 с `WWW-Authenticate: Bearer` (`96-99`, `241-242`).
- Порядок конвейера корректен: exception handler первым, BR32 после аутентификации и до авторизации (`Program.cs:180-191`) → отказ выглядит как истечение сессии, а не как ролевое решение.
- `UserActivityTracker` потокобезопасен (`ConcurrentDictionary` + `lock` на prune) и память ограниченна prune по 8 ч; успешный login сбрасывает baseline (`AuthController.cs:71`), активность продлевается любым аутентифицированным запросом (`Middleware.cs:262-271`).
- BR20 (последний активный администратор) защищён на уровне контроллера (`UsersController.cs:296-309`), audit-логи читает только `AdminOnly` (`AdminController.cs:16`), сид Development-only (`Program.cs:171-177`).
